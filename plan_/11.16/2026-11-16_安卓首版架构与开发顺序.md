# Lumi 安卓首版：架构与开发顺序

**日期：** 2026-11-16　｜　**状态：** 已确定的开发方向，尚未真机验证

Lumi 要做的是一台在按快门前帮普通人发现更好拍法的相机。首版以「旅行时帮朋友在拱门前拍照」为验证场景：相机发现可以用门洞框住人物，在取景器里用白点、绿环和引导线带用户调整机位与手机朝向。用户可以边挪步边转动、仰俯手机；如果一个动作就让人和拱顶都拍好了，相机应直接提示可以拍。

**第一个真机里程碑：给定一个拱门拍法，验证相机能否可靠地把用户带到位。** 下一阶段再验证 AI 能否主动发现值得尝试的拍法。这样，试拍失败时可以区分是「选错了拍法」，还是「选对了，但没带到位」。

## 1. 技术选择与职责

安卓原生开发，采用 **Kotlin + CameraX + Jetpack Compose**，不绑定具体机型。先建一个 Gradle 应用模块 `:app`，按以下五个 Kotlin 包组织代码。这是职责边界，无需一开始就拆成五个 Gradle 模块。

| 包 | 职责 | 对外输出 |
| --- | --- | --- |
| `camera` | 管理相机生命周期、预览、分析帧和拍照，维护分析画面与预览之间的坐标映射。 | 带采集时间、旋转及裁切信息的分析帧；拍照结果。 |
| `vision` | 检测、持续跟踪当前人物和背景。首版尝试随应用打包的 ML Kit 人脸检测；用局部图像特征跟踪已选中的门柱和拱顶。手机姿态辅助区分转动和横移。 | 同一帧中的人脸、门边、拱顶位置，以及目标是否可见、跟踪是否可信。 |
| `shotplan` | 选定主体、背景和目标构图。仅在首次稳定取景、用户换拍法或原目标失效时重新选择。 | 与具体人物和拱门关联的拍法，例如「让脸落进门洞、拱顶完整、左右取景合适」。 |
| `guidance` | 用纯 Kotlin 比较当前观察与拍法，同时评估各项条件，生成动作提示并判断能否拍摄。不依赖 CameraX、Compose 或特定模型。 | 绿环相对白点的偏移、动作类型（挪步或转动手机等）、引导状态和就绪状态。 |
| `ui` | 在 CameraX 的 `PreviewView` 上叠加 Compose Canvas，绘制白点、绿环与引导线，展示快门及到位反馈。 | 用户看到的取景器；按快门时向 `camera` 发出拍照请求。 |

首个里程碑只覆盖后置 1×、竖屏、单人和拱门，不要求后端、ARCore 或大模型逐帧运行。可信地识别合适的背景，是自动推荐阶段的任务；人脸检测只能解决「人在哪里」。

## 2. 数据怎样从相机走到绿环

```text
CameraX ── Preview ──────────────────────────────→ PreviewView 取景底图
   │
   └── ImageAnalysis → vision → 最新观察 ───────────┐
                                   │                │
                      需要选拍法时 └→ shotplan       │
                                       ↓            ↓
                                    当前拍法  +  最新观察
                                              ↓
                                           guidance
                                              ↓
                                绿环偏移、动作提示、能否拍摄
                                              ↓
                                        ui 叠加显示

用户按快门 → camera 拍照（任何引导状态下均可触发）
```

模块之间传递三种信息即可，以下是数据含义，不是已经定版的接口：

- **观察：** 这一帧何时采集、跟踪的是谁和哪道门、各自在画面哪里、哪些部分看不清。分析跟不上时保留最新帧，分析结束后释放帧；旧结果不能覆盖新结果。
- **拍法：** 保存目标身份和构图条件，不保存第一帧的固定像素，也不保存动作清单。手机一动，门在屏幕上的位置会变，「用这道门框住她」仍然成立。
- **引导：** 表达当前值得做的调整。坐标先统一到考虑旋转与裁切的取景参考系，再映射到实际预览。绿环到白点的距离表达剩余调整量，不表示现实中的米数；白点是取景准星，不代替相机对焦点。

## 3. 拱门示例：一次组合动作如何完成拍摄

| 时刻 | 系统判断 | 取景器反馈 |
| --- | --- | --- |
| 举起手机 | 朋友的脸叠在左门柱上，右侧是门洞，拱顶也被裁掉一部分。当前拍法要求人脸与门柱分开，同时保留拱顶。 | 中央白点固定；绿环出现在左上方，虚线连接两点，配「左挪 · 微仰」，区分挪脚和转手机。 |
| 边左移、边右转、边仰拍 | 每次有效观察都重新检查脸和门边的相对位置、拱顶留白及左右取景。只原地转手机、脸仍贴着门柱时，不计作横移成功。 | 脸逐渐进入门洞，横向偏移收小；拱顶留白已合适，纵向偏移消失。不再要求用户重复仰拍。 |
| 条件同时满足 | 连续的新鲜、可信观察均表明构图在可拍范围内，且短暂停稳。用户先挪后仰、先仰后挪或同时调整，都可以达到同一结果。 | 两点合拢，提示「可以拍了」，随后淡出辅助标记。由用户选择表情和按快门的时机。 |
| 被遮挡或明显偏离 | 看不清人或门时，当前构图是「未知」；一帧合格后失去跟踪，不能靠旧坐标或动画计时宣布到位。 | 不可信时淡出引导；重新认出目标后再继续。达标后的小幅手抖留有容差，明显偏离才恢复提示。 |

绿环可做平滑显示，但**是否可以拍由真实观察决定，不由动画是否重合决定**。观察的新鲜度、稳定时长、容差及跟踪恢复条件留到真机试拍标定。

## 4. 开发顺序与验收

| 阶段 | 先交付什么 | 通过条件 |
| --- | --- | --- |
| **M1：相机与坐标** | 跑通预览、分析和照片保存。在分析画面上标一个可辨认的真实位置，将标记画回取景器。 | 移动或转动手机时，标记仍贴在同一处；在约定的输出比例下，保存照片的关键构图边界与预览一致。先排除坐标错位，再判断算法好坏。 |
| **M2：双点引导闭环** | 测试时允许手动指定门洞及拱顶，绑定人物后持续跟踪。接入纯 Kotlin 的 `guidance` 与真实相机叠层。这一步的手动标注是测试入口，不是正式用户流程。 | 原地转动不会冒充挪步；不同调整顺序得到相同就绪结果；一个组合动作完成就直接可拍；快速掠过合适构图、目标被挡或观察过期时都不误报。保留代表性的观察序列，用于重放验证。 |
| **M3：自动发现拍法** | 在同一批场景上，用自动推荐替换手动指定入口，继续复用 M2 的跟踪、引导和到位判断。先比较推荐结果，再决定是否引入多模态模型。 | 用户不指定拱门，相机也能选中值得利用的人景关系。对比普通拍摄与引导拍摄的成片，让被拍者在不知道来源时选更愿意保留的一张，并记录哪些建议没带来改善。 |

**开工顺序：先做 M1 的「预览里标得准」，再做 M2 的「实景里带得到」，最后做 M3 的「主动选得好」。** M2 是第一个可交给用户试拍的版本；M3 才验证完整的主动推荐体验。
