# Lumi 安卓首版：架构与开发顺序

**日期：** 2026-11-16（11-17 修订交互模型、开发状态与可复用方案）　｜　**状态：** M1 已收尾；M2 已实现，待真机验收；下一步 M3 接入大模型推荐构图

Lumi 要做的是一台在按快门前帮普通人发现更好拍法的相机。**AI 直接给出一个推荐构图，用户把手机移到这个构图上去**，而不是先指出问题、再提醒用户怎么改。首版以「旅行时帮朋友在拱门前拍照」为验证场景：AI 选定「朋友落在门洞里、拱顶完整、上方留一点空间」这张画面，取景器里用两点一线把用户带过去。

- **白点**固定在屏幕中心，只是给用户的视觉坐标。
- **绿环**标出推荐构图在当前取景器里的位置。
- **连线**连接两点。两点决定一条线，用户一眼就知道该往哪边调，不需要读「左移一点、再抬高」这样的文字指令。

用户可以一边挪步，一边转动或仰俯手机。白点始终居中，绿环和连线随真实取景变化而更新。一个动作就拍出了选定的画面时，两点合拢，提示可以拍，由用户按快门。**两点和线是执行方案的界面，AI 选好的那张构图才是方案本身。**

**开发路线：先尽快做出「AI 给方案、两点一线拍出来」的完整闭环，再扩大能拍到的构图范围。** 第一版 AI 只推荐转动或仰俯手机就能拍到的构图，与 Doka、LiveCapture 的覆盖范围相同；拱门这类需要挪步的构图放到后面。「记住这个构图」保留为调试入口，用来单独检查绿环准不准，这样试拍失败时仍能区分是「选错了构图」，还是「选对了，但没带到位」。

## 1. 技术选择与职责

安卓原生开发，采用 **Kotlin + CameraX + Jetpack Compose**，不绑定具体机型。一个 Gradle 应用模块 `:app`，按以下五个 Kotlin 包组织代码。这是职责边界，无需拆成五个 Gradle 模块。

| 包 | 职责 | 对外输出 |
| --- | --- | --- |
| `camera` | 管理相机生命周期、预览、分析帧和拍照，维护分析画面与预览之间的坐标映射。Preview、ImageAnalysis、ImageCapture 共用同一个 `ViewPort`。 | 带采集时间、旋转及裁切信息的分析帧；拍照结果。 |
| `vision` | 检测、持续跟踪推荐构图所依托的人物和背景。首版尝试随应用打包的 ML Kit 人脸检测；用局部图像特征跟踪门柱和拱顶。手机姿态用于在两帧观察之间估算画面转动。 | 同一帧中的人物、门边、拱顶位置，以及目标是否可见、跟踪是否可信。 |
| `shotplan` | 选定推荐构图：主体、背景及它们在画面中的目标关系。仅在首次稳定取景、用户换构图或原目标失效时重新选择。 | 与具体人物和拱门关联的推荐构图，例如「脸落进门洞、拱顶完整、上方留白」。 |
| `guidance` | 用纯 Kotlin 比较当前观察与推荐构图，算出绿环应在取景器的哪里，判断两点是否已合拢。不依赖 CameraX、Compose 或特定模型。 | 绿环位置、引导是否可信、是否已到位。 |
| `ui` | 在 CameraX 的 `PreviewView` 上叠加 Compose Canvas，绘制白点、绿环与连线，展示快门及到位反馈。不显示文字动作指令。 | 用户看到的取景器；按快门时向 `camera` 发出拍照请求。 |

首版只覆盖后置 1×、竖屏、单人。大模型只在用户请求推荐时调用一次，不逐帧运行；是否用 ARCore 估计挪步，在 M4 评估（见第 5 节）。可信地识别合适的背景，是自动推荐阶段的任务；人脸检测只能解决「人在哪里」。

## 2. 数据怎样从相机走到绿环

```text
CameraX ── Preview ──────────────────────────────→ PreviewView 取景底图
   │
   └── ImageAnalysis → vision → 最新观察 ───────────┐
                                   │                │
                      需要选构图时 └→ shotplan       │
                                       ↓            ↓
                                  推荐构图  +  最新观察
                                              ↓
                                           guidance
                                              ↓
                                绿环位置、是否可信、是否到位
                                              ↓
                                     ui 绘制白点、绿环、连线

用户按快门 → camera 拍照（任何引导状态下均可触发）
```

模块之间传递三种信息即可，以下是数据含义，不是已经定版的接口：

- **观察：** 这一帧何时采集、跟踪的是谁和哪道门、各自在画面哪里、哪些部分看不清。分析跟不上时保留最新帧，分析结束后释放帧；旧结果不能覆盖新结果。
- **推荐构图：** 保存目标身份和构图关系，不保存第一帧的固定像素，也不保存动作清单。手机一动，门在屏幕上的位置会变，「用这道门框住她」仍然成立。
- **引导：** 绿环在取景参考系中的位置，再映射到实际预览。绿环到白点的距离表达离推荐构图还差多少，不表示现实中的米数；白点是视觉坐标，不代替相机对焦点。

**待真机验证的实现问题：绿环位置怎么算。** 如果推荐构图只靠转动或仰俯手机就能拍到，绿环就是推荐画面的中心在当前取景中的投影，可由画面跟踪结合手机姿态直接算出。如果需要挪步才能拍到，例如要让脸和门柱分开，推荐画面不在当前取景之内，绿环要由人和门的相对位置还差多少来推算。两种情况对用户都只呈现同一个绿环；前一种在 M2、M3 实现，后一种在 M4 实现，都要用真机标定。

## 3. 拱门示例：一次组合动作如何完成拍摄

这是 M4 完成后的目标体验；M3 只覆盖其中靠转动或仰俯就能拍到的部分。

| 时刻 | 系统判断 | 取景器反馈 |
| --- | --- | --- |
| 举起手机 | 朋友的脸叠在左门柱上，拱顶被裁掉一部分。推荐构图是脸落进门洞、拱顶完整、上方留白。 | 中央白点固定；绿环出现在左上方，连线指向它。 |
| 边左移、边右转、边仰拍 | 每次有效观察都重新比较当前画面与推荐构图，更新绿环位置。只原地转手机、脸仍贴着门柱时，不能算作接近推荐构图。 | 绿环和连线随取景实时移动，逐渐靠近白点。用户先挪后仰、先仰后挪或同时调整都可以。 |
| 两点合拢 | 连续的新鲜、可信观察均表明当前画面已在推荐构图的可拍范围内，且短暂停稳。 | 两点合拢，提示可以拍，随后淡出辅助标记。由用户选择表情和按快门的时机。 |
| 被遮挡或明显偏离 | 看不清人或门时，当前位置是「未知」；一帧合格后失去跟踪，不能靠旧坐标或动画计时宣布到位。 | 不可信时淡出绿环和连线；重新认出目标后再继续。到位后的小幅手抖留有容差，明显偏离才重新出现绿环。 |

绿环可做平滑显示，但**是否到位由真实观察决定，不由动画是否重合决定**。观察的新鲜度、稳定时长、容差及跟踪恢复条件留到真机试拍标定。

## 4. 开发顺序与验收

| 阶段 | 交付内容 | 通过条件 |
| --- | --- | --- |
| **M1：相机与坐标（已收尾）** | 预览、分析、拍照保存；分析帧到取景器的坐标映射（`FrameGeometry`，有单元测试）；三路共用 `ViewPort`。 | 已在 PKX110 真机跑通：照片写入相册，构图与预览大致一致，前后台切换恢复正常。点选跟踪器（`PatchTracker`）和四边比对工具（`tools/m1_framing`）只作调试工具保留，不在产品路径上，不再继续投入。 |
| **M2：转动可达的两点一线（已实现，待真机验收）** | 调试入口「记住这个构图」：测试者摆好构图并记录，转开手机，再跟着绿环回来。用镜头内参和手机姿态投影绿环，并核对人脸和背景（`RotationGuidance`）。 | 绿环方向正确；回到目标并停稳后合拢；快速掠过、人脸被挡或观察过期时不误报到位。 |
| **M3：大模型推荐构图（下一步）** | 用户点「推荐构图」，把当前画面发给多模态大模型一次，模型返回推荐构图的新取景中心。以发送那一帧的手机姿态为基准，把推荐中心当作目标方向，复用 M2 的投影、绿环和到位判断。只推荐转动或仰俯手机就能拍到、保持 1× 的构图。参考 Drama 的结构化协议和提示词。 | 在真实场景中，用户点一次推荐，就能跟着绿环转到推荐构图并合拢；等待模型返回期间手机移动，绿环仍指向正确方向；请求失败、超时或返回不合法时不画绿环。对比普通拍摄与推荐拍摄的成片，让被拍者在不知道来源时选更愿意保留的一张，并记录哪些推荐没带来改善。 |
| **M4：需要挪步的构图** | 拱门这类需要挪步、改变人和背景相对位置才能拍到的构图（见第 3 节）。先按第 5 节对比 ARCore、OpenCV 和现有方案，选定后再实现。 | 原地转动不会被当成已接近需要挪步才能拍到的构图；不同调整顺序得到相同的到位结果；一个组合动作完成就直接合拢。 |

**开发顺序：M1「预览里标得准」和 M2「转动带得到」已完成，接下来做 M3「AI 给方案」，形成完整闭环后再做 M4「挪步也带得到」。** M3 是第一个可交给用户试拍的版本。

## 5. 可复用的开源项目与平台能力

**原则：新增一项能力前，先查平台能力和开源实现，确认没有合适方案再自己写。** 自己写的代码集中在 Lumi 的差异点：持续识别具体的人和背景，在需要挪步的构图上也能把用户带到位。

| 来源 | 内容 | 用法 |
| --- | --- | --- |
| [Drama](https://github.com/tommycyl/Drama)（MIT，Expo/React Native） | 大模型一次返回新的取景中心 `aimPoint`；屏幕中心、虚线、目标圈；陀螺仪本地移动目标圈，停稳 800 毫秒判定可拍。只按约 60° 视场角估算转动，不做画面跟踪；平移需要用户手动确认。作者注明尚未在 Android 真机验证。 | M3 接入大模型时，参考它的 [结构化协议](https://github.com/tommycyl/Drama/blob/main/docs/camera-guidance-protocol.md) 和提示词。代码技术栈不同，不直接引入。 |
| [LiveCapture / LiveCompose](https://github.com/LiveCompose/LiveCapture)（iOS，**未声明开源协议**） | 自训练裁切模型预测推荐构图框，陀螺仪跟踪并带磁吸效果，到位自动拍。只覆盖转动和变焦能到达的构图。 | 只参考思路，不复制代码。其模型的使用许可不明确，M3 若想对比需先确认授权。 |
| ML Kit | 人脸检测带跟踪 ID；目标检测与跟踪；人体姿态；人像分割。 | 人物识别和跟踪优先用 ML Kit，不自写跟踪器。 |
| OpenCV | 特征点检测、金字塔光流、单应矩阵与本质矩阵估计。 | 跟踪门柱、拱顶等背景结构，估计视差时优先使用。引入前评估安装包体积和每帧耗时。 |
| ARCore | 六自由度相机位姿，可直接得到摄影者的平移量。 | M4 的候选方案。代价是只支持部分机型，且与 CameraX 共用相机需走 Shared Camera（Camera2），拍照分辨率和现有架构都要评估。 |
| CameraX `CoordinateTransform` / `MlKitAnalyzer` | 把分析帧上的检测结果映射到 `PreviewView`。 | 现有 `FrameGeometry` 已测试并在使用，不替换；新增的映射需求优先用 CameraX 自带接口。 |

Open Camera、PhotonCamera 为 GPL 协议，且以相机工程和成像为主，不作为底座。

实现参考：[CameraX 图像分析](https://developer.android.com/media/camera/camerax/analyze) · [CameraX 预览坐标变换](https://developer.android.com/media/camera/camerax/transform-output) · [ML Kit 模型打包方式](https://developers.google.com/ml-kit/tips/installation-paths)
