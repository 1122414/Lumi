# Lumi M3 推荐构图：重构与下一步开发指导

**日期：** 2026-11-18　｜　**适用代码：** `d1d721c` 之后　｜　**上位文档：** [安卓首版架构与开发顺序](../11.16/2026-11-16_安卓首版架构与开发顺序.md)

## 1. 现状

M3 已经跑通「点推荐 → 模型返回 → 绿环引导 → 可以拍」的完整链路，并按试拍反馈加入了蓝色主体轮廓、十字以内的推荐理由和变焦。但真机体验不可用，具体表现为：

| 现象 | 证据 |
| --- | --- |
| 蓝色轮廓不贴主体，线条杂乱 | 11-18 用玩偶试拍的截图和反馈 |
| 绿环闪烁、跳动，方向和位置经常不对，转开再转回后常找不回 | 11-18 多轮试拍反馈：「绿环还是不行，方向经常不对，位置也不对」 |
| 经常显示「取景未确定」「已识别主体，暂无可信构图」，推荐用不了 | 两次玩偶推荐模型都返回了 HTTP 200，但被手机端校验拒绝 |
| 推荐等待长 | 实测一次：准备 0.2 秒，模型 5.9 秒，本地核对 0.2 秒 |

值得注意的是，**M2 只用手机姿态加人脸投影绿环时，11-18 上午的试拍反馈是「绿环跟得住，停稳后提示可以拍」**。体验是在后续加入「按主体实测位置校准绿环」和逐帧轮廓之后变差的。

## 2. 根因

一天内连续 15 次提交，每次针对一个症状加修正或加校验，但没有解决下面三个结构性问题。

1. **让大模型直接给像素坐标。** 现在的提示词要求模型输出主体框（0–1000）、主体内一点和推荐中心。通用多模态模型擅长判断「拍什么、怎么拍更好」，不擅长给出精确坐标。框不准，后面的分割、轮廓、校验和绿环都跟着错。
2. **绿环位置由多路证据混合计算，并被大量状态门控。** 绿环同时受手机姿态投影、主体实测位置反推的姿态、`RingContinuity` 平滑、`ReturnDirection` 边缘处理影响，`GuideEvidence` 有 11 种状态，任何一项校验不过，绿环就隐藏或跳到另一套算法给出的位置。分割结果每帧抖一点，绿环就跟着跳或消失。
3. **每帧都跑交互式分割。** 主体跟随期间，每帧都对裁切图运行 Magic Touch 分割再提取轮廓。分割本身每帧不一致，轮廓自然杂乱，而且耗费分析帧时间。

## 3. 方向：AI 只做选择题，几何交给手机

| 环节 | 现在 | 改为 |
| --- | --- | --- |
| 找主体 | 大模型给主体框和内部点 | 手机端检测器（ML Kit 人脸、目标检测）给出候选框并编号，画在发给模型的图上，模型只回答选几号 |
| 推荐构图 | 大模型给推荐中心坐标 | 手机按选中的主体生成几种构图选项（主体在左三分、右三分、居中，头顶留白多或少，保持现状），模型只回答选哪一项和十字理由；坐标全部由手机算 |
| 绿环 | 姿态投影与主体实测位置混合，多状态门控 | 推荐一旦成立，绿环只由手机姿态投影，连续显示、不再因校验隐藏；转出画面时贴边指回（保留现有贴边逻辑） |
| 蓝色轮廓 | 每帧重新分割 | 只在推荐那一帧分割一次得到轮廓，之后按手机姿态投影移动；主体是静止的人或物时足够准确 |
| 可以拍 | 多项视觉校验加停稳 | 绿环与白点的角度差在容差内并停稳；低频检查主体还在预期位置附近，主体明显走开时提示重新推荐 |

这样做的取舍：

- **主体移动时绿环不会跟着主体走。** 旅行人像中被拍者通常站定摆姿势；主体明显移动时，提示重新推荐即可。
- **模型只能在手机给出的几种构图里选。** 换来坐标精确、结果可预期、几乎不会被拒绝。选项不够用时再增加选项，不回到让模型给坐标。
- **蓝色轮廓在主体移动后会偏。** 与上一条一样，靠重新推荐解决。

## 4. 开发阶段

| 阶段 | 交付 | 通过条件 |
| --- | --- | --- |
| **M3.0 模型接口入口** | 取景界面上方增加「模型」入口，显示当前模型名和连接状态；点开后可填写接口地址、模型名和 API key，测试连接并保存。保存后立即生效，不需要改 `local.properties` 或重新打包。`local.properties` 中的三项只作为 debug 版首次启动的默认值。 | 在手机上改成另一个模型后，下一次推荐就使用新模型，调试记录中能看到所用模型；测试连接能区分地址不可达、鉴权失败、模型不支持图片和成功，并显示耗时；API key 输入时默认隐藏，存储时加密，不出现在日志和界面明文中；推荐进行中修改配置，旧请求作废、旧推荐清除。 |
| **M3.1 稳定引导** | 绿环改为纯姿态投影；轮廓只在推荐帧分割一次并按姿态移动；「可以拍」改为角度容差加停稳；界面状态只保留「推荐中」「引导中」「可以拍」和失败提示。推荐协议暂不改。 | 推荐成立后，在主体静止、只转动手机的 30 秒内：绿环每帧都显示，不闪烁；手机静止时绿环抖动不超过画宽 1%；朝推荐方向转动时，绿环到白点的距离持续减小；转开 90° 再转回，绿环贴边指回并回到原推荐位置；停稳约 0.6 秒才提示可以拍，快速掠过不提示；轮廓与主体的偏差不超过主体宽度的 10%。 |
| **M3.2 推荐改成选择题** | 手机端生成编号的主体候选和构图选项；提示词和返回协议改为「选主体编号、选构图选项、十字理由」；没有检测到候选主体时，回退到现有的模型给框方式。 | 同一批 10 个场景（人和静物各半）中，至少 9 次能给出推荐，「暂无可信构图」类拒绝不超过 1 次；模型选中的主体与人工判断一致的不少于 8 次；模型输出不超过 60 个字符，推荐总等待时间中位数不超过 3 秒（取决于所用模型服务）。 |
| **M3.3 外场试拍** | 模型接口改为不依赖 USB 也能访问（见第 5 节）；在真实旅行或街拍场景各拍一组「普通拍法」和「跟随推荐」。 | 被拍者在不知道来源时，从每组中选更愿意保留的一张；记录推荐被选中的比例，以及哪些推荐没有带来改善。 |
| **M4 需要挪步的构图** | 按上位文档执行，M3.3 结论出来后再启动。 | 见上位文档。 |

M3.0 改动小、与引导逻辑无关，先做；它也让 M3.1、M3.2 的试拍可以随时换用更快的模型。变焦已按你的要求实现，后续阶段沿用「改变倍率即清除旧推荐」的规则，不再扩展。

## 5. 需要你决定的事项

1. **模型接口能否脱离 USB。** 现在的 `http://127.0.0.1:3425/v1` 依赖 `adb reverse`，手机必须连着电脑，没法去真实景点试拍。M3.0 让手机上可以直接填写接口，但 M3.3 之前仍需要一个手机直接可达的 HTTPS 地址（云端服务或可公网访问的代理）。
2. **所用模型是否适合看图。** `workbuddy/deepseek-v4.1-flash` 一次实测要 5.9 秒，并多次给出低置信度。M3.0 完成后可以在手机上直接切换模型；M3.2 之后用同一批场景对比一两个其他视觉模型的选择质量和耗时，再决定是否更换。
3. **debug 版是否允许任意 HTTP 地址。** 填写局域网电脑的地址（例如 `http://192.168.x.x:3425/v1`）就能脱离 USB 线在室内测试，但 Android 默认禁止明文 HTTP，网络安全配置也无法按用户输入的地址动态放行。M3.0 的做法是：debug 版允许明文 HTTP，并在非本机地址使用 HTTP 时提示风险；release 版只允许 HTTPS。若不接受这一点，debug 版仍只放行 `127.0.0.1`。

## 6. 给 Codex 的工作规则

过去几天的偏差有一半来自工作方式，以下规则写进每次提示词：

- **每个阶段开一个新会话，**只附本文档和上位文档，不在同一个超长会话里连续修补。
- **同一个问题修两次仍未解决，就停下汇报，**列出可能的原因和备选方案，由人决定，不继续叠加修正。
- **不为解决症状新增校验或状态。**新增任何会让绿环隐藏或让推荐被拒绝的条件，都要先在汇报里说明理由。
- **到停止点就停，**真机反馈的新需求先记录，等这一阶段验收后再排期。
